# درسنامهٔ پرامپت سیستمی Gemini CLI

## در یک جمله

این پرامپت سیستمی اصلی Gemini CLI در Google است: یک مدل بزرگ عمومی را به Agent مهندسی نرم‌افزار خط فرمانی محدود می‌کند که «اول امنیت، اول قراردادها و نهایت کوتاهی» را رعایت می‌کند.

## چرا ارزش یاد گرفتن دارد

- از معدود پرامپت‌های سیستمی کامل و عمومی‌خوانای **Agent کدنویس ترمینال** است؛ ساختارش روشن و ماژول‌هایش جدا از هم‌اند و نمونهٔ خوبی برای نوشتن پرامپت Agent است.
- «تغییر امن کد در مخزن واقعی» را به دنباله‌ای از قدم‌های قابل‌اجرا تقسیم کرده (فهمیدن ← برنامه‌ریزی ← پیاده‌سازی ← راستی‌آزمایی)، نه شعار کلی.
- بین «انجام پیش‌قدمانهٔ کار» و «فراتر نرفتن از اختیار و گسترش ندادن خودسرانهٔ دامنه» تعادل ظریفی برقرار کرده است؛ دقیقاً سخت‌ترین بخش پرامپت Agent.
- با استفادهٔ زیاد از واژه‌های وجهی قوی (NEVER، MUST، VERY IMPORTANT) و مثال نقض مشخص، نشان می‌دهد چطور به قیدها «دندان» بدهیم.
- در پایان با چند گفت‌وگوی `<example>` قاعده‌های انتزاعی را به نمونه‌های رفتاری قابل‌تقلید گره می‌زند؛ مادهٔ آموزشی خوبی برای هم‌ترازی سبک با few-shot.

## ساختار پرامپت، بخش به بخش

### ۱. تعریف هویت

جملهٔ اول هویت را تعیین می‌کند: «یک Agent تعاملی CLI متخصص کارهای مهندسی نرم‌افزار» و فوراً اولویت را می‌دهد: امنیت، کارایی، پیروی دقیق از دستورها و استفادهٔ خوب از ابزارها.

- **مشکلی که حل می‌کند:** مدل از همان ابتدا به شخصیت باریک «مهندس داخل ترمینال» برسد، نه دستیار عمومی.
- **چه چیزی خوب نوشته شده:** هویت + هدف + منبع قید (دستورها و ابزارها) در یک جمله، بدون داستان پس‌زمینهٔ زائد.
- **قابل‌استفادهٔ دوباره:** `تو یک Agent {شکل} متخصص {حوزه} هستی. هدف اصلی‌ات کمک به کاربر به شکلی {ارزش ۱} و {ارزش ۲} است، با پیروی دقیق از دستورهای زیر و استفادهٔ خوب از ابزارهای در دسترس.`

### ۲. مرز امنیتی

در چند جا پخش است، `Security and Safety Rules`، `Outside of Sandbox` و `Respect User Confirmations`، و لایه‌به‌لایه محافظت می‌کند:

- دستوری که وضعیت سیستم را تغییر می‌دهد **باید** پیش از اجرا هدف و اثرش توضیح داده شود؛ اما **لازم نیست** جداگانه اجازه خواست (به پنجرهٔ تأیید رابط کاربری سپرده شده). این از فاجعهٔ تجربهٔ کاربری «برای هر قدم پرسیدن» جلوگیری می‌کند.
- **هرگز** کدی ننویس که secretها را افشا، در لاگ ثبت یا commit کند.
- وقتی بیرون از sandbox اجرا می‌شود، باید به کاربر یادآوری کند sandbox را فعال کند؛ «خطر محیط» صریحاً گفته می‌شود.
- فراخوانی‌ای را که کاربر لغو کرده نباید دوباره و دوباره امتحان کرد.
- **چه چیزی خوب نوشته شده:** دو چیز را از هم جدا کرده: «توضیح دادن» و «اجازه خواستن»؛ هم حس امنیت هست و هم روانی.
- **قابل‌استفادهٔ دوباره:** سه‌گانهٔ «پیش از اقدام پرخطر هدف و اثر را توضیح بده + به سازوکار تأیید بیرونی اعتماد کن + به رد کاربر احترام بگذار».

### ۳. فراخوانی ابزار

بخش `Tool Usage` قواعد استفاده از ابزار را بسیار مهندسی نوشته است:

- مسیر مطلق اجباری است (با رهنمود جداگانهٔ `Path Construction` و نمونهٔ ترکیب مسیر).
- فراخوانی‌های مستقل **موازی** باشند.
- دستور ماندگار با `&` در پس‌زمینه؛ دستور تعاملی تا جای ممکن با نسخهٔ غیرتعاملی (`npm init -y`).
- ابزار `save_memory` فقط برای ترجیح‌های **شخصی کاربر** بین جلسه‌هاست و صریحاً می‌گوید context پروژه را **ذخیره نکن**؛ مرز ابزار حافظه را کشیده است.
- **قابل‌استفادهٔ دوباره:** برای هر ابزار «کی استفاده کن / کی هرگز / شرط‌های مرزی» را روشن بنویسید؛ از فقط فهرست کردن نام ابزارها خیلی مؤثرتر است.

### ۴. روند کار (دومسیره)

دو نوع کار را جدا می‌کند و برای هر کدام روند متفاوتی می‌دهد:

- **کارهای مهندسی نرم‌افزار:** فهمیدن ← برنامه‌ریزی ← پیاده‌سازی ← راستی‌آزمایی (تست) ← راستی‌آزمایی (استانداردها)؛ تأکید بر ساختن فهم با grep و glob در ابتدا، ساختن چرخهٔ خودراستی‌آزمایی با تست واحد، و هرگز فرض نکردن دستور تست.
- **برنامه‌های تازه:** نیاز ← پیشنهاد ← تأیید کاربر ← پیاده‌سازی خودکار ← راستی‌آزمایی ← گرفتن بازخورد، همراه با «جدول انتخاب پیش‌فرض وقتی پشتهٔ فناوری مشخص نشده».
- **چه چیزی خوب نوشته شده:** یک Agent در برابر «تغییر کد موجود» و «ساختن چیز تازه» ریتم متفاوتی دارد؛ کار روی کد موجود بر احتیاط و راستی‌آزمایی تأکید می‌کند و کار تازه اجازه می‌دهد خودکار تا نمونهٔ اولیهٔ قابل‌اجرا جلو برود.
- **قابل‌استفادهٔ دوباره:** «اول شناسایی (recon) بعد دست به کار شدن + راستی‌آزمایی اجباری پایانی (build، lint، بررسی نوع)» اسکلت طلایی Agent کدنویس است.

### ۵. سبک خروجی

بخش `Tone and Style` برای موقعیت CLI تنظیم شده: «کمتر از ۳ خط»، «گپ نزن»، «بدون پیش‌درآمد و پس‌گفتار»، «ابزار کار می‌کند و متن فقط برای ارتباط است».

- **مشکلی که حل می‌کند:** تجربهٔ خواندن در ترمینال بد است و خروجی پرحرف نویز است.
- **قابل‌استفادهٔ دوباره:** سه قید سخت «سقف طول خروجی + ممنوعیت پرکننده + تقسیم کار ابزار و متن» فوراً Agent را تمیزکارتر می‌کند.

### ۶. همکاری با کاربر و کنترل دامنه

بخش `Proactiveness` می‌خواهد اقدام‌های بعدی ضمنی کامل انجام شوند، اما `Confirm Ambiguity/Expansion` تعیین می‌کند نباید از اختیار فراتر رفت و دامنه را گسترش داد؛ «اگر پرسیدند چطور، اول توضیح بده و مستقیم انجام نده». بخش Git هم همین را نشان می‌دهد: پیش‌نویس پیام commit را می‌نویسد اما خودسرانه push نمی‌کند.

- **چه چیزی خوب نوشته شده:** با یک جفت قاعده که به ظاهر متضادند، مرز دقیق «پیش‌قدمی» را تعیین می‌کند.
- **قابل‌استفادهٔ دوباره:** «کارهای فرعی‌ای را که مستقیم از درخواست برمی‌آیند پیش‌دستانه کامل کن، اما پیش از هر اقدام مهمِ بیرون از دامنهٔ روشن تأیید بگیر.»

### ۷. تثبیت با نمونه‌های few-shot

مجموعهٔ `<example>` پایانی لحن و روند کار را پیاده می‌کند: `1+2 → 3` (نهایت کوتاهی)، پیش از بازسازی دنبال تور ایمنی تست گشتن (احتیاط)، و پیش از حذف پوشه گفتن پیامد (امنیت).

- **قابل‌استفادهٔ دوباره:** بلافاصله بعد از قاعده‌های انتزاعی ۲ تا ۶ نمونهٔ مقایسه‌ای بیاورید؛ خطای برداشت مدل از «اندازه» به‌طور محسوسی کم می‌شود.

## الگوهای قابل‌استفادهٔ دوباره

- **یک جمله برای تثبیت هویت + ترتیب اولویت‌ها.**
- **روند کار دومسیره:** کار روی کد موجود (شناسایی ← برنامه ← پیاده‌سازی ← دو بار راستی‌آزمایی) و کار تازه (نیاز ← پیشنهاد ← تأیید ← پیاده‌سازی ← راستی‌آزمایی ← بازخورد).
- **سه‌گانهٔ امنیتی:** پیش از کار پرخطر توضیح بده + به تأیید بیرونی اعتماد کن + به لغو احترام بگذار.
- **قالب قواعد ابزار:** برای هر ابزار کاربرد، مرز و مثال نقض را مشخص کن.
- **قید سخت خروجی:** سقف خط + ممنوعیت پرکننده + تقسیم کار ابزار و متن.
- **واژهٔ وجهی قوی + مثال نقض:** NEVER و MUST را با موقعیت مشخص همراه کن، نه با توصیهٔ کلی.
- **هم‌ترازی دولایه با قاعده + نمونه‌های مقایسه‌ای few-shot.**

## چه چیزهایی را نباید عیناً کپی کرد

- **نام ابزارها مخصوص Gemini CLI‌اند** (`run_shell_command`، `replace`، `read_many_files`، `save_memory`، `glob`، `search_file_content`)؛ در سکوی دیگر باید با مجموعه ابزار خودتان عوض شوند، وگرنه مدل خیال فراخوانی ابزارهای ناموجود را می‌کند.
- **جدول انتخاب فناوری پیش‌فرض (React+Bootstrap، FastAPI، Three.js و…) گرایش شدیدی دارد** و لزوماً با پشتهٔ فناوری تیم شما جور نیست؛ کپی مستقیمش اسکلت‌های ناخواسته‌ای می‌سازد.
- **«خروجی کمتر از ۳ خط» برای محصولات آموزشی یا توضیحی بیش از حد خسیس است**؛ دستیاری که برای مبتدی‌هاست با کپی کردنش سرد به نظر می‌رسد.
- **«لازم نیست اجازه بخواهی، به پنجرهٔ تأیید رابط کاربری سپرده شده» به سازوکار تأیید میزبان وابسته است**؛ اگر محیط اجرای شما چنین سازوکاری ندارد، کپی کردنش یعنی دستور خطرناک بی‌نگهبان می‌ماند.
- **یادآوری بیرون از sandbox** فقط وقتی معنا دارد که واقعاً مستقیم روی سیستم کاربر اجرا شود.

## موضوع‌هایی برای درس‌های بعدی

1. نوشتن «روند کار دومسیره» برای Agent و توضیح تفاوت ریتم کار روی کد موجود و ساختن چیز تازه.
2. طراحی قواعد امنیتی: جدا کردن توضیح از اجازه، اعتماد به سازوکار تأیید بیرونی و معنای لغو.
3. چطور قواعد فراخوانی ابزار بنویسیم که توهم کمتر شود (سه‌بخشی کاربرد، مرز و مثال نقض).
4. قید سبک خروجی در موقعیت CLI و ترفند تثبیت با few-shot.
5. این‌که «پیش‌قدمی» و «کنترل دامنه» چطور با یک جفت قاعده دقیق تعریف می‌شوند.

> پیشنهاد: این درسنامه را کنار درسنامه‌های Claude Code و Codex CLI بخوانید تا امنیت و روند کار Agentهای کدنویس را افقی مقایسه کنید. منبع این متن عکس لحظه‌ای بی‌تاریخی است و تأیید نشده؛ برای استفاده، نسخهٔ رسمی تازه ملاک است.
