# درسنامهٔ ماژول‌های پرامپت Manus

## در یک جمله

این متن کامل «پرامپت سیستمی ماژولار» Agent عمومی Manus است. Agentی را که می‌تواند در sandbox لینوکس خودکار کار کند، به ده‌ها ماژول قاعده تقسیم می‌کند که هر کدام با یک برچسب XML مشخص شده است (جریان رویداد، agent loop، planner، knowledge، datasource و قواعد انواع عملیات). نمونه‌ای مرجع برای این است که «یک سیستم خودکار پیچیده را چطور با پرامپت ساختارمند بسته‌بندی کنیم».

## چرا ارزش یادگرفتن دارد

با پرامپت‌هایی که فقط «تعیین نقش + چند قاعده» هستند فرق دارد و **مدل ذهنی کامل یک Agent خودکار در سطح تولید** را نشان می‌دهد:

- اول تعریف می‌کند Agent جهان را چطور درک می‌کند (هفت نوع رویداد در جریان رویداد)، بعد ریتم اقدامش را (شش مرحلهٔ agent loop)، و فقط در آخر قیدهای مشخص هر حوزه را می‌دهد. این لایه‌بندی «ادراک، چرخه، قواعد حوزه» اسکلت رایج پرامپت‌های بزرگ Agent است.
- ماژول‌های سیستم بیرونی (Planner، Knowledge، Datasource) را صریحاً وارد می‌کند و به مدل می‌گوید «این رویدادها را سیستم تولید کرده و لازم نیست جواب بدهی». نشان می‌دهد پرامپت چطور با زمان اجرای چندماژولی هماهنگ می‌شود، نه این‌که فقط یک LLM منفرد را محدود کند.
- برای هر نوع ابزار (shell، browser، file، deploy، message) بلوک قاعدهٔ مستقلی دارد که جداگانه خوانده می‌شود؛ نگه‌داری، گسترش و آزمایش A/B را آسان می‌کند.
- پشت بیشتر قیدها انگیزهٔ محصولی قابل‌حدسی هست (هزینه، دسترس‌پذیری، ردپذیری، امنیت). برای یادگرفتن «چرا این‌طور نوشته شده» مادهٔ خوبی است.

## ساختار پرامپت، بخش به بخش

### ۱. تعریف هویت و توانایی (intro و system_capability)

با یک جمله هویت را تعیین می‌کند (Manus، ساختهٔ تیم Manus)، بعد با `<intro>` شش نوع کاری را که در آن مهارت دارد فهرست می‌کند و با `<system_capability>` توانایی‌های محیطی را که می‌تواند فراخوانی کند. **فهرست توانایی از هویت جداست**: اولی رو به کاربر می‌گوید «چه کاری از من برمی‌آید» و دومی رو به مدل می‌گوید «چه اهرم‌هایی در دست دارم».

### ۲. لایهٔ ادراک: جریان رویداد (event_stream)

تنها کانال ورودی Agent را تعریف می‌کند: جریانی از رویدادها که به ترتیب زمان مرتب شده و ممکن است بریده شده باشد. هفت نوع رویداد را برمی‌شمارد: Message، Action، Observation، Plan، Knowledge، Datasource و بقیه. این پایهٔ شناختی کل پرامپت است؛ همهٔ ماژول‌های بعدی بر این فرض بنا شده‌اند که «من جهان را با خواندن جریان رویداد می‌فهمم».

### ۳. لایهٔ اقدام: agent loop

با یک چرخهٔ ثابت شش‌مرحله‌ای (تحلیل رویداد ← انتخاب ابزار ← انتظار برای اجرا ← تکرار ← تحویل ← آماده‌باش) ریتم Agent را محدود می‌کند و «در هر دور فقط یک فراخوانی ابزار» را اجباری می‌کند. سیستم خودکار باز را به چرخه‌ای تک‌قدمی، پیش‌بینی‌پذیر و قابل‌اشکال‌زدایی تبدیل می‌کند.

### ۴. پروتکل ماژول‌های بیرونی (planner، knowledge، datasource)

این سه بلوک در اصل «شرح پروتکل گفت‌وگو با سیستم‌های دیگر زمان اجرا» هستند: planner برنامه‌ای با شبه‌کد شماره‌دار می‌دهد، knowledge بهترین شیوه‌هایی با دامنهٔ کاربرد مشخص می‌دهد، و datasource API دادهٔ معتبر. بخش datasource نمونه‌کد `weather.py` هم دارد و تصریح می‌کند «API داده فقط با کد Python فراخوانی می‌شود، ابزار نیست و نتیجه‌اش باید در فایل ذخیره شود».

### ۵. قواعد عملیاتی حوزه‌ها (todo، message، file، info، browser، shell، coding، deploy، writing، error_handling)

بدنهٔ اصلی پرامپت همین است و هر بلوک XML یک نوع عملیات را مدیریت می‌کند:

- بلوک **todo_rules**: فایل todo.md فهرست پیشرفت قابل‌دیدن است و قاعده این است که «برنامه بر todo.md مقدم است، اما todo.md جزئیات بیشتری دارد».
- بلوک **message_rules**: بین notify (غیرمسدودکننده) و ask (مسدودکننده) فرق می‌گذارد، اولین پاسخ را فقط به تأیید دریافت محدود می‌کند و خروجی‌ها را به شکل پیوست می‌خواهد.
- بلوک **info_rules**: اولویت اطلاعات را روشن می‌کند (API داده > جست‌وجوی وب > دانش داخلی) و تأکید می‌کند خلاصهٔ نتیجهٔ جست‌وجو منبع نیست و باید صفحهٔ اصلی را باز کرد.
- بلوک **browser_rules**: قالب شاخص عنصرها `index[:]<tag>text</tag>`، محدودیت viewport و ناقص بودن متن Markdown استخراج‌شده را تعریف می‌کند.
- بلوک‌های **shell_rules، coding_rules و deploy_rules**: بیشتر جزئیات عملیاتی‌اند (تأیید خودکار با -y و -f، ذخیرهٔ کد در فایل پیش از اجرا، گوش دادن سرویس روی 0.0.0.0).
- بلوک **writing_rules**: سبک نوشتن متن بلند را سخت محدود می‌کند (اولویت با نثر، حداقل چند هزار کلمه، اول پیش‌نویس جداگانه و بعد الحاق، و ممنوعیت کوتاه کردن در نسخهٔ نهایی).

### ۶. مرزها و فراقواعد (error_handling، sandbox_environment، tool_use_rules)

در پایان نردبان بازیابی از خطا (بررسی پارامتر ← رفع بر اساس پیام خطا ← تغییر روش ← کمک خواستن از کاربر)، واقعیت‌های سخت محیط sandbox (Ubuntu 22.04 و نسخه‌های Python و Node) و فراقواعد «استفاده از ابزار» (پاسخ حتماً با فراخوانی تابع، نبردن نام ابزار پیش کاربر، نساختن ابزار خیالی) آمده‌اند.

## الگوهای قابل‌استفادهٔ دوباره

- **اسکلت سه‌بخشی «ادراک ← چرخه ← قواعد حوزه»**: برای هر Agentی که چند ابزار دارد و در چند دور خودکار اجرا می‌شود قابل‌استفاده است: اول ورودی را تعریف کنید (جریان رویداد یا قالب context)، بعد چرخهٔ تک‌قدمی را، و در آخر قاعدهٔ هر حوزه را.
- **هر بار فقط یک ابزار**: با یک قید سخت، هم‌زمانی و آشفتگی پشت در می‌ماند و اشکال‌زدایی بسیار آسان‌تر می‌شود. برای طراحی Agent در شروع کار، باارزش‌ترین قاعده برای کپی کردن همین است.
- **بلوک‌بندی با برچسب XML**: برای هر حوزه یک برچسب معنایی (`<shell_rules>`، `<browser_rules>`…) تا قاعده‌ها پیدا شوند، جداگانه اضافه یا حذف شوند و پرامپت‌های دیگر بتوانند به آن‌ها ارجاع دهند.
- **سطح‌بندی ارتباط (notify و ask)**: «مزاحم کاربر شدن» را به دو سطح اقدام صریح تبدیل می‌کند و پیش‌فرض را بر غیرمسدودکننده می‌گذارد؛ الگوی خوبی برای تعادل استقلال و تجربهٔ کاربر.
- **اولویت صریح منبع اطلاعات**: با ترتیب «دادهٔ معتبر > جست‌وجو > دانش داخلی» با توهم مقابله می‌کند و اضافه می‌کند «خلاصه منبع نیست، صفحهٔ اصلی را باز کن».
- **نمایش پیشرفت (todo.md) + اعلام اولویت برنامه**: کار طولانی محملی بیرونی، دیدنی و قابل‌اصلاح برای وضعیتش پیدا می‌کند و روشن است که بین todo.md و برنامهٔ بالادستی حرف کدام مقدم است.
- **نردبان بازیابی از خطا**: بررسی ← رفع ← تغییر مسیر ← کمک خواستن؛ به مدل ترتیب روشنی برای رسیدگی به شکست می‌دهد، به جای تلاش بی‌پایان.

## چه چیزهایی را نباید عیناً کپی کرد

- **وابستگی شدید به زمان اجرای خود Manus**: ماژول‌های planner، knowledge و datasource، مسیر `/opt/.manus/.sandbox-runtime`، ابزار expose port و `data_api.ApiClient` همه زیرساخت اختصاصی Manus‌اند. بدون زمان اجرای مشابه، کپی کردنشان به توانایی‌هایی اشاره می‌کند که وجود ندارند.
- **واقعیت‌های سخت sandbox کهنه می‌شوند**: Ubuntu 22.04، Python 3.10.12 و Node 20.18.0 عکس لحظه‌ای ثابتی از محیط‌اند. با تغییر محیط باید هم‌زمان به‌روز شوند، وگرنه مدل را گمراه می‌کنند.
- **قواعد نوشتن بیش از حد تند است**: «حداقل چند هزار کلمه»، «طول نهایی باید از مجموع همهٔ پیش‌نویس‌ها بیشتر باشد» و «تقریباً همیشه فهرست ممنوع» انتخاب‌های لحن محصول Manus‌اند و برای بیشتر کاربردها (به‌ویژه دستیاری که باید مختصر باشد) ضدالگو هستند.
- **«نبردن نام ابزار پیش کاربر» راهبرد محصول است**: جایی که رفتار ابزار باید شفاف گفته شود، به کار نمی‌آید.
- **فرض API داده که «هزینه با سیستم است و ورود لازم نیست»**: این از بسته‌بندی تجاری Manus می‌آید؛ سیستمی که خودتان می‌سازید معمولاً باید احراز هویت و سهمیه را خودش مدیریت کند.

## موضوع‌هایی برای درس‌های بعدی

- **لایهٔ ادراک Agent**: جریان رویداد چیست، چرا Message، Action و Observation صریحاً دسته‌بندی شده‌اند و با بریدگی و حذف چطور کنار می‌آییم.
- **تبدیل سیستم خودکار به چرخهٔ تک‌قدمی**: شش مرحلهٔ agent loop و سود اشکال‌زدایی که «هر بار فقط یک ابزار» به همراه دارد.
- **هماهنگی پرامپت با ماژول‌های بیرونی**: طراحی پروتکل planner، knowledge و datasource، و قراردادهایی مثل «رویداد سیستمی جواب لازم ندارد».
- **مهندسی بلوک‌بندی XML برای قواعد حوزه**: تقسیم قاعده‌ها بر اساس ابزار و عملیات، طوری که نگه‌داری‌پذیر، قابل‌ارجاع و قابل‌انتشار تدریجی باشند.
- **مهار توهم و شکست با پرامپت**: اولویت منبع اطلاعات، این‌که خلاصهٔ جست‌وجو منبع نیست، و نردبان بازیابی از خطا.
- **سطح‌بندی ارتباط انسان و ماشین**: فلسفهٔ طراحی notify در برابر ask و مرز کاربردش.

> نکته: این درسنامه را کنار درسنامه‌های «پرامپت سیستمی Manus» و «چرخهٔ Agent در Manus» بخوانید. آن دو هویت و چرخهٔ اصلی را توضیح می‌دهند و این یکی جزئیات قواعد هر حوزه را.
