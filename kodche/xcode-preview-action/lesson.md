# درسنامهٔ پرامپت Preview Action در Xcode

## در یک جمله

این پرامپت ابزاری «تک‌کاره» در هوش مصنوعی داخلی Xcode است: با گرفتن فایل فعلی کاربر و View انتخاب‌شدهٔ SwiftUI، کد ماکروی `#Preview` مناسب آن را خودکار می‌سازد و فقط خود کد را برمی‌گرداند.

## چرا ارزش یاد گرفتن دارد

این پرامپت بسیار خویشتن‌دار است و هدفی کاملاً واحد دارد؛ در تضاد آشکار با پرامپت‌های Agent عمومی که گاهی هزار خط می‌شوند. ارزشش در این است که نشان می‌دهد «ابزار با کار محدود» را چطور باید نوشت:

- ورودی با جای‌نگهدارهای قالب (`{{filename}}`، `{{filecontent}}`، `{{selected}}`) تزریق می‌شود و ساختار روشنی دارد.
- قالب خروجی سخت محدود شده است (فقط `#Preview`، حتماً داخل بلوک کد، بدون توضیح).
- قواعد کاری به شکل جدول تصمیم «شرط ← اقدام» آمده‌اند که مدل تقریباً می‌تواند مثل if/else اجرایشان کند.

برای یاد گرفتن این‌که یک تکه دانش حوزه (بهترین شیوه‌های SwiftUI Preview) را چطور در پرامپت بگذاریم، نمونهٔ بسیار فشرده‌ای است.

## ساختار پرامپت، بخش به بخش

### ۱. تعریف هویت

این پرامپت بند هویتی صریحی از نوع «You are…» ندارد؛ نقش را مستقیم با context و کار تعریف می‌کند. اول به مدل می‌گوید کاربر در کدام فایل است، محتوای فایل چیست و چه چیزی انتخاب شده، بعد با یک جمله، «Your task is to create a Preview for a SwiftUI View»، مدل را به یک وظیفهٔ واحد میخ‌کوب می‌کند. این شیوهٔ معمول پرامپت‌های ابزاری است: هویت در خود کار پنهان است و توکنی صرف شخصیت‌سازی نمی‌شود.

### ۲. مرز امنیتی

«مرز امنیتی» این پرامپت مرز خروجی است، نه مرز دسترسی:

- «only return the code for the #Preview macro with no additional explanation»؛ حاشیه رفتن و توضیح دادن ممنوع است.
- در انتها دوباره تأکید می‌کند «Return the #Preview and no additional explanation» و می‌خواهد «ALWAYS wrap the preview in triple-tick markdown code snippet marks».

یک قید هم در ابتدا و هم در انتها تکرار شده تا با اثر «تقدم و تأخر» با تمایل مدل به توضیح دادن مقابله شود. این «قرارداد خروجی» پیش‌شرط وصل کردن نتیجه به روند درج خودکار در IDE است، چون برنامهٔ میزبان به قالبی پایدار و قابل‌تجزیه نیاز دارد.

### ۳. فراخوانی ابزار

دقیق‌تر بگوییم، خودش ابزاری است که فراخوانی می‌شود (یکی از actionهای هوش مصنوعی Xcode) و در داخلش ابزار دیگری فراخوانی نمی‌کند. نکتهٔ قابل‌توجه این است که امضای سازندهٔ `#Preview` را مستقیم به مدل می‌دهد:

```text
init(_ name: String? = nil, body: @escaping @MainActor () -> any View)
```

و یک نمونهٔ حداقلی هم کنارش می‌گذارد. این یعنی مستندات API را در پرامپت جا داده تا احتمال این‌که مدل API را اشتباه به یاد بیاورد کم شود.

### ۴. جدول تصمیم قواعد حوزه

هستهٔ پرامپت جدول قواعدی از نوع «شرط فعال‌ساز ← اقدام بسته‌بندی» است:

- اگر `.navigation*`، `NavigationLink`، `.toolbar*` و مانند آن دیده شد ← داخل `NavigationStack` بگذار.
- اگر modifierهایی مثل `.listRow*` و `.listItem*` دیده شد یا نام پسوند `Row` داشت ← داخل `List` بگذار.
- اگر فهرستی از نوع‌ها می‌گیرد ← ۵ دادهٔ ساختگی بساز.
- اگر `@Binding` می‌گیرد ← همان‌جا داخل `#Preview` تعریفش کن.
- متغیرهای static یا global موجود را دوباره به کار ببر، مخصوصاً برای تصویرها.
- بی‌دلیل `@availability` اضافه نکن.

نمونه‌ای عالی از صریح کردن «تجربهٔ ضمنی مهندس هنگام نوشتن Preview» است.

## الگوهای قابل‌استفادهٔ دوباره

- **سه‌گانهٔ context**: نام فایل فعلی + محتوای کامل فایل + تکهٔ انتخاب‌شده. ساختار استاندارد تزریق برای پرامپت‌های «اقدام روی کد درون ویرایشگر» است و مستقیم برای تکمیل، بازسازی و توضیح کد هم کار می‌کند.
- **قید خروجی دوبار، در آغاز و پایان**: قالب خروجی را در ابتدا اعلام کنید و در انتها دوباره تأکید کنید؛ پایداری قالب به‌طور محسوسی بالا می‌رود.
- **امضای API + نمونهٔ حداقلی**: وقتی مدل باید کد یک چارچوب را بسازد، امضای API هدف و یک نمونهٔ hello-world را مستقیم بدهید؛ از توضیح صرفاً متنی مطمئن‌تر است.
- **جدول تصمیم شرط و اقدام**: بهترین شیوه‌های حوزه را به شکل فهرست «اگر الگوی X دیده شد، Y را انجام بده» بنویسید؛ رفتار مدل قطعی‌تر می‌شود.
- **پیش‌فرض: منابع موجود را دوباره به کار ببر** (متغیرهای static و global): مدل کمتر دادهٔ آزمایشی از خودش می‌سازد.

## چه چیزهایی را نباید عیناً کپی کرد

- قواعد پر از توصیف‌های شبیه wildcard‌اند (مثل `.navigation.*`) و به تطبیق تقریبی مدل تکیه می‌کنند. در جایی که عبارت منظم ممکن است مبهم باشد، به‌راحتی اشتباه تشخیص داده می‌شوند؛ معنای تطبیق را دقیق کنید.
- قید سخت «فقط کد بده و توضیح نده» عیب‌یابی را در مرحلهٔ اشکال‌زدایی سخت می‌کند. اگر محصول شما به توضیح‌پذیری نیاز دارد، راهی برای توضیح باز بگذارید.
- این پرامپت به‌شدت به اکوسیستم SwiftUI و Xcode گره خورده است. خود جدول قواعد منتقل نمی‌شود؛ فقط روش «نوشتن جدول تصمیم» قابل‌انتقال است.

## موضوع‌هایی برای درس‌های بعدی

- طراحی ساختار تزریق ورودی و قرارداد خروجی برای «پرامپت ابزاری با کار محدود».
- تبدیل تجربهٔ متخصص حوزه به جدول تصمیم «شرط ← اقدام».
- کاربرد اثر تقدم و تأخر در قیدهای خروجی پرامپت.
- ترفند «مستندات درون‌خطی»: گذاشتن امضای API و نمونهٔ حداقلی در پرامپت.
