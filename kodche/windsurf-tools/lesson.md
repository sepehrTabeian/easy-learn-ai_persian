# درسنامهٔ تعریف ابزارهای Windsurf (Wave 11)

## در یک جمله

این **فهرست کامل تعریف ابزارهایی** است که Windsurf (IDE هوش مصنوعی ساختهٔ Codeium که Agentش Cascade نام دارد) در نسخهٔ Wave 11 در اختیار مدل می‌گذارد. با امضای تابع TypeScript و کامنت درون‌خطی، همهٔ توانایی‌هایی را که یک Agent کدنویس لازم دارد (خواندن و نوشتن فایل، بازیابی، ترمینال، مرورگر، استقرار، حافظه، MCP) یک‌جا اعلام می‌کند.

## چرا ارزش یادگرفتن دارد

- این یک schema ابزار **واقعی در سطح تولید** است، نه نمونهٔ آموزشی. نشان می‌دهد یک Agent پختهٔ IDE دقیقاً به چه ابزارهایی نیاز دارد و مرز پارامترهای هر ابزار چطور تقسیم شده.
- با قالبی بسیار ساده اما پراطلاعات (نوع TS + کامنت به‌عنوان مستندات) هم‌زمان دو نقش دارد: «schema قابل‌تجزیه برای ماشین» و «راهنمای استفاده برای خواندن مدل».
- در توضیح هر ابزار انبوهی **قید ضدسوءاستفاده** نشسته است (کی نباید فراخوانی کرد، سقف‌ها، تشخیص امنیتی، ترتیب پارامترها)؛ نمونهٔ خوبی برای یادگرفتن «چطور با زبان طبیعی برای ابزار نرده بگذاریم».
- مجموعهٔ ابزارها کل چرخهٔ Agent کدنویس را پوشش می‌دهد: فهمیدن ← تغییر ← راستی‌آزمایی ← استقرار ← حافظه؛ می‌شود از رویش نقشهٔ توانایی یک محصول Agent را بازسازی کرد.

## ساختار، بخش به بخش

### ۱. نمای کلی مجموعه ابزار

همهٔ ابزارها داخل یک `namespace functions` تعریف شده‌اند و در انتها یک `multi_tool_use.parallel` برای فراخوانی موازی آمده است. بر اساس کارکرد، شش دسته‌اند:

| دسته | ابزارها |
| --- | --- |
| بازیابی و مرور کد | `codebase_search`، `grep_search`، `find_by_name`، `list_dir`، `view_file`، `view_code_item` |
| ویرایش فایل | `replace_file_content`، `write_to_file` |
| اجرای ترمینال | `run_command`، `command_status`، `read_terminal` |
| مرورگر و وب | `browser_preview`، `open_browser_url`، `read_browser_page`، `get_dom_tree`، `capture_browser_screenshot`، `capture_browser_console_logs`، `list_browser_pages`، `read_url_content`، `view_content_chunk`، `search_web` |
| استقرار | `read_deployment_config`، `deploy_web_app`، `check_deploy_status` |
| حافظه، MCP و همکاری | `create_memory`، `list_resources`، `read_resource`، `trajectory_search`، `suggested_responses` |

نکتهٔ قابل‌توجه این است که «بازیابی» به سه ریزدانگی تقسیم شده: بازیابی معنایی (`codebase_search`)، تطبیق دقیق با regex (`grep_search`) و جست‌وجوی نام فایل (`find_by_name`)، و در توضیح‌ها موقعیت مناسب و مرز ناکارآمدی هر کدام روشن شده است.

### ۲. طراحی ابزارهای کلیدی

- **ابزار `codebase_search` (بازیابی معنایی)**: توضیحش صریحاً به مدل می‌گوید «پرس‌وجو هرچه دقیق‌تر بهتر»، «سؤال گسترده نتیجهٔ بد می‌دهد»، «بیش از ۵۰۰ فایل کیفیت را به‌شدت کم می‌کند» و «فقط موارد بالایی کامل نشان داده می‌شوند و بقیه فقط امضا». ویژگی‌های واقعی موتور جست‌وجو به قید رفتاری مدل ترجمه شده تا مدل از جست‌وجوی معنایی برای سوزن در انبار کاه سوءاستفاده نکند.
- **ابزار `replace_file_content` (ویرایش)**: پرقیدترین ابزار کل فهرست است. با ۵ قاعدهٔ شماره‌دار مدل را محدود می‌کند: یک فایل را موازی ویرایش نکن، برای چند تغییر از چند `ReplacementChunk` استفاده کن، `TargetContent` باید نویسه‌به‌نویسه (با فاصله‌ها) با متن اصلی مطابقت کند، کل فایل را جایگزین نکن (پرهزینه است) و `.ipynb` را ویرایش نکن. این یک قرارداد «ویرایش به شکل diff» است که از بازنویسی کل فایل کم‌توکن‌تر و کنترل‌پذیرتر است.
- **ابزار `run_command` (ترمینال)**: انبوهی معنای امنیتی در آن نشسته است: ممنوعیت `cd`، قاعدهٔ انتخاب بین مسدودکننده و غیرمسدودکننده، معیار تشخیص `SafeToAutoRun` (حذف فایل، تغییر وضعیت، نصب وابستگی و درخواست بیرونی همه ناامن‌اند)، و اصل سخت «حتی اگر کاربر بخواهد، دستور ناامن را هرگز خودکار اجرا نکن».
- **ابزار `create_memory` (حافظه)**: سه حالت create، update و delete را تعریف می‌کند و می‌خواهد «پیش از ساختن، دنبال نمونهٔ تکراری بگرد»؛ منطق حذف تکرار پایگاه دادهٔ حافظه را به خود مدل سپرده است.
- **خانوادهٔ ابزارهای مرورگر**: با `PageId` به‌عنوان دستگیره، زنجیرهٔ کامل باز کردن ← فهرست ← خواندن ← اسکرین‌شات ← لاگ کنسول را به هم وصل می‌کند؛ طراحی توانایی «Agent مثل انسان صفحهٔ وب را ببیند».

### ۳. قیدهای پارامتر و امنیت

آموزنده‌ترین بخش این فهرست **الگوهای قیدی است که بارها تکرار می‌شوند**:

- **اجبار `toolSummary` در ابتدا**: تقریباً هر ابزار یک `toolSummary?` دارد و کامنتش تأکید می‌کند «باید پیش از همهٔ پارامترهای دیگر مشخص شود؛ حتی اگر جای دیگری گفته شده چیز دیگری اول بیاید، این مقدم است». هدف این است که رابط کاربری فوراً نشان دهد «Agent دارد چه کار می‌کند» و مشاهده‌پذیری بالا برود.
- **سقف نتیجه**: `find_by_name` و `grep_search` سقف سخت ۵۰ مورد دارند و `codebase_search` و `trajectory_search` هم محدود شده‌اند و دربارهٔ بریده شدن هشدار می‌دهند، تا context زیر نتیجه‌های جست‌وجو غرق نشود.
- **اعلام وابستگی پیشین**: `check_deploy_status` باید بعد از `deploy_web_app` باشد، `deploy_web_app` باید اول `read_deployment_config` را داشته باشد، و `view_content_chunk` به خوانده شدن قبلی سند وابسته است. ترتیب وابستگی فراخوانی ابزارها با زبان طبیعی صریحاً اعلام شده.
- **«اجرا نکن مگر کاربر بخواهد»**: ابزارهای مخرب یا پرمصرف مثل `check_deploy_status` آستانهٔ فعال‌سازی انسانی دارند.

### ۴. طراحی خود قالب بیان

کل سند با اعلان نوع TS به شکل `type نام_ابزار = (_: {...}) => any;` نوشته شده و کامنت پارامترها مستقیم بالای هر فیلد آمده است. مزیت این قالب: برای مدل ساختاریافته و کم‌ابهام است؛ برای آموزش و تجزیه قابل‌خواندن با ماشین است؛ و در عین حال کامنت‌ها مستندات به زبان طبیعی‌اند. یک محتوا هم‌زمان در خدمت سه طرف است.

## الگوهای قابل‌استفادهٔ دوباره

- **لایه‌بندی سه‌ریزدانگی بازیابی**: برای جست‌وجوی معنایی، regex و نام فایل هر کدام یک ابزار بسازید و در توضیح، موقعیت مناسب و مرز ناکارآمدی هر کدام را بنویسید تا مدل ابزار درست را انتخاب کند.
- **قرارداد ویرایش به شکل diff**: به جای بازنویسی کل فایل، از «TargetContent با تطبیق دقیق + ReplacementContent + چند تکه» استفاده کنید؛ الگوی کم‌هزینه و پربازدهٔ ویرایش فایل برای Agent.
- **توضیح ابزار همان نرده است**: «کی نباید استفاده کرد»، «سقف چقدر است»، «وابستگی پیشین» و «تشخیص امنیتی» را مستقیم در description بنویسید، نه این‌که به پرامپت سیستمی بیرونی تکیه کنید.
- **فیلد یکسان `toolSummary`**: برای مشاهده‌پذیری، روی هر ابزار یک خلاصهٔ یک‌جمله‌ای پیشرفت بگذارید و تولیدش در ابتدا را اجباری کنید.
- **علامت سطح امنیت**: با پارامترهای بولی مثل `SafeToAutoRun` بگذارید مدل خودش خطر را بسنجد و کنارش قاعدهٔ سخت عبورناپذیر بگذارید.

## چه چیزهایی را نباید عیناً کپی کرد

- **وابستگی به سکو**: `run_command` ثابت نوشته `Operating System: windows. Shell: powershell.`، `deploy_web_app` به Netlify و فهرست مشخصی از چارچوب‌ها گره خورده، و ابزارهای حافظه، مرورگر و استقرار به زیرساخت زمان اجرای Windsurf وابسته‌اند؛ بیرون از Windsurf مستقیم قابل‌استفاده نیستند.
- **قالب استاندارد عمومی نیست**: این سبک کامنت TS داخلی Windsurf است، نه JSON Schema در function calling شرکت OpenAI؛ انتقال به چارچوب دیگر تبدیل لازم دارد.
- **قیدها مقدار تجربی‌اند**: سقف ۵۰ مورد و آستانهٔ ۵۰۰ فایل عددهایی‌اند که برای پیاده‌سازی خود Windsurf تنظیم شده‌اند و برای موتور بازیابی دیگری لزوماً مناسب نیستند.
- **تشخیص امنیتی `SafeToAutoRun`** ارزیابی خطر را به مدل سپرده است؛ در تولید باید یک لایهٔ قطعی فهرست سفید و سیاه هم رویش گذاشت و فقط به خودآگاهی مدل تکیه نکرد.

## موضوع‌هایی برای درس‌های بعدی

- «چطور برای یک ابزار description بنویسیم»: با `codebase_search` و `run_command` به‌عنوان نمونه، تفاوت رفتار مدل را پیش و پس از اضافه کردن قید مقایسه کنید.
- «ویرایش فایل به شکل diff در برابر بازنویسی کل فایل»: انگیزهٔ طراحی `replace_file_content` و اقتصاد توکن آن.
- «نقشهٔ توانایی Agent کدنویس»: با همین فهرست بازسازی کنید یک Agent کامل IDE به چند دسته ابزار نیاز دارد و چرخهٔ فهمیدن ← تغییر ← راستی‌آزمایی ← استقرار را رسم کنید.
- «وابستگی و ترتیب فراخوانی بین ابزارها»: با سه‌تایی استقرار (config ← deploy ← status) به‌عنوان نمونه، قیدهای هماهنگ‌سازی را توضیح دهید.
- «طراحی مشاهده‌پذیری Agent»: ملاحظات محصولی پشت اجبار `toolSummary` در ابتدا.

> نکته: این درسنامه را کنار درسنامهٔ «پرامپت سیستمی Windsurf» بخوانید تا تصویر کامل «پرامپت رفتار را تعیین می‌کند + schema ابزار توانایی را» دیده شود. منبع این متن تأیید نشده و تاریخ نسخهٔ مشخصی ندارد؛ آن را سند رسمی Wave 11 ندانید.
