# درسنامهٔ پرامپت سیستمی Roo Code

## در یک جمله

متن: Roo Code یک Agent کدنویسی چندحالته (Code، Architect، Ask، Debug، Boomerang) برای VS Code است. پرامپت سیستمی‌اش با قراردادهای متنی ساده و پروتکل ابزار XML، حلقهٔ امن «یک ابزار در هر قدم + تأیید کاربر» را در هر تعامل جا داده است.

## چرا ارزش یادگرفتن دارد

- **نمونهٔ کلاسیک پروتکل ابزار بدون function calling بومی.** ابزارها را با برچسب‌های XML تعریف می‌کند؛ پس روی هر مدل زبانی خام می‌شود توانایی Agent را بازسازی کرد.
- **«حالت» (mode) را مفهوم درجه‌یک کرده است.** با همان ابزارها، فقط با تعریف نقش و محدودیت فایل قابل‌ویرایش، چند Agent تخصصی ساخته می‌شود. نمونهٔ خوبی از «با پرامپت کم، چند شخصیت».
- **امنیتش خویشتن‌دار است.** هر بار فقط یک ابزار، انتظار اجباری برای تأیید نتیجه و خودبازبینی پیش از `attempt_completion`؛ الگوی قابل‌انتقال برای «جلوگیری از رها شدن».
- **توضیح ابزارها پر از نمونهٔ درست است.** چند مثال برای `read_file` و `apply_diff` ابهام را از بین می‌برد؛ نمونهٔ درسی «رفع ابهام با مثال».

## ساختار پرامپت، بخش به بخش

### ۱. تعریف هویت

شروع پرامپت فقط دو جمله است: «مهندس نرم‌افزار بسیار ماهر» و «کار را با کم‌ترین تغییر در کد و با تمرکز بر قابلیت نگهداری انجام بده».

- **چه مشکلی را حل می‌کند:** شخصیت مهندس آرام و خویشتن‌دار می‌دهد تا مدل تغییر بزرگ یا خودنمایی نکند.
- **نکتهٔ خوب:** هویت و ارزش (کم‌ترین تغییر، قابلیت نگهداری) در یک جمله بسته شده، که از انبوه صفت مؤثرتر است.
- **قالب قابل‌استفادهٔ دوباره:** «تو {نقش} هستی و کار را با {قید اصلی} انجام می‌دهی، با تمرکز بر {هدف کیفیت}.»
- **عیناً کپی نکنید:** ارزش «کم‌ترین تغییر» برای ویرایش کدبیس موجود طراحی شده؛ در محصول «تولید از صفر» باید عکسش را بخواهید، یعنی خروجی کامل.

### ۲. مرز امنیتی (قواعد + حلقهٔ تأیید ابزار)

مرکز ثقل کل پرامپت است و بین سه جا پخش شده: «راهنمای استفاده از ابزار»، «قواعد» و توضیح `attempt_completion`.

- **اجرای تک‌قدمی:** «در هر پیام یک ابزار» و «پیش از ادامه منتظر تأیید باش». کارهای بازگشت‌ناپذیر به کوچک‌ترین واحد قابل‌بازبینی شکسته می‌شوند.
- **جعبه‌شنی پوشه:** نمی‌توان با `cd` از فضای کار بیرون رفت، مسیرها نسبی‌اند و `~` و `$HOME` ممنوع‌اند؛ دامنهٔ سیستم فایل قفل می‌شود.
- **قانون نوشتن کامل:** `write_to_file` باید محتوای کامل فایل را بگیرد و جای‌نگهدارهایی مثل `// rest unchanged` اکیداً ممنوع‌اند؛ مدل نمی‌تواند از سر تنبلی فایل را خراب کند.
- **خودبازبینی:** پیش از `attempt_completion` باید در `<thinking>` از خود بپرسد که موفقیت ابزارهای قبلی تأیید شده یا نه.
- **قالب قابل‌استفادهٔ دوباره:** «یک ابزار، منتظر نتیجه، بعد تصمیم»؛ «در نوشتن کل فایل، حذف با جای‌نگهدار ممنوع است».
- **عیناً کپی نکنید:** تأیید دستی هر قدم توان عملیاتی را می‌خواباند. در Agent تمام‌خودکار باید جایش را «بازگرداندن خودکار نتیجه» بگیرد.

### ۳. فراخوانی ابزار (پروتکل XML)

- به‌جای API بومی ابزارها، قرارداد `<tool_name><param>value</param></tool_name>` را به کار می‌برد.
- هر ابزار ساختار مستند یکسان دارد: **توضیح + جدول پارامتر + قالب Usage + چند مثال**.
- ابزار `apply_diff` از بلوک SEARCH/REPLACE با شمارهٔ خط استفاده می‌کند و `read_file` خواندن بازهٔ خط را برای فایل‌های بزرگ پشتیبانی می‌کند؛ هر دو برای صرفه‌جویی توکن و دقت طراحی شده‌اند.
- **قالب قابل‌استفادهٔ دوباره:** «چهاربخشی مستندسازی ابزار» (توضیح، پارامتر، الگو، نمونه) بهترین شیوهٔ کاهش خطای فراخوانی است.
- **عیناً کپی نکنید:** پروتکل XML سازشی برای نبودن function calling است. اگر مدل زیرین فراخوانی بومی دارد، همان را اولویت بدهید؛ تجزیه‌اش پایدارتر است.

### ۴. حالت‌ها و هماهنگی (MODES + switch_mode + new_task)

- پنج حالت داخلی ابزار مشترک دارند، ولی تعریف نقش و **الگوی regex فایل‌های قابل‌ویرایش** فرق می‌کند؛ مثلاً حالت architect فقط `\.md$` را می‌تواند ویرایش کند.
- ابزار `switch_mode` به Agent اجازه می‌دهد خودش درخواست تغییر نقش بدهد، `new_task` کار فرعی می‌سازد، و حالت Boomerang مخصوص هماهنگی و واگذاری کار است.
- **قالب قابل‌استفادهٔ دوباره:** «تعریف نقش + ماتریس دسترسی فایل/ابزار» یعنی چندعاملی سبک، بدون بازنویسی کل ابزارها برای هر Agent.

### ۵. زمینه و گسترش‌پذیری (environment_details، فایل‌های `.roo/rules` و MCP)

- بخش `environment_details` (درخت فایل‌ها و ترمینال‌های در حال اجرا) خودکار تزریق می‌شود، اما پرامپت صریحاً می‌گوید «آن را درخواست کاربر حساب نکن».
- دستورهای سفارشی به‌صورت لایه‌ای از `.roo/rules/` و `.roo/rules-code/` بارگذاری می‌شوند و فایل `.roo/system-prompt-code` کل پرامپت را بازنویسی می‌کند.
- پروتکل MCP به‌عنوان نقطهٔ گسترش ابزار و منبع در دو نوع محلی (Stdio) و راه‌دور (SSE) آمده است.
- **قالب قابل‌استفادهٔ دوباره:** جدا کردن صریح «زمینهٔ خودکار تزریق‌شده» از «قصد واقعی کاربر» در پرامپت، تا مدل نویز را با دستور اشتباه نگیرد.

### ۶. سبک خروجی

- شروع پیام با «Great»، «Certainly»، «Okay» و «Sure» ممنوع است؛ لحن مستقیم، فنی و بدون تعارف.
- پایان `attempt_completion` **پرسش ندارد** و باید نتیجهٔ نهایی باشد.
- **قالب قابل‌استفادهٔ دوباره:** «شروع با {کلمه‌های تعارف} ممنوع؛ نتیجه باید نهایی باشد و با سؤال تمام نشود.»

## الگوهای قابل‌استفادهٔ دوباره

- **مستندسازی چهاربخشی ابزار:** توضیح، پارامتر (با علامت الزامی/اختیاری)، الگوی استفاده، چند مثال.
- **حلقهٔ امن تک‌قدمی:** یک ابزار + انتظار برای تأیید + خودبازبینی پیش از اتمام.
- **ماتریس نقش × دسترسی:** یک مجموعه ابزار + تعریف نقش‌های مختلف + فهرست سفید فایل‌های قابل‌ویرایش = چند Agent تخصصی.
- **جداسازی محیط از قصد:** زمینهٔ خودکار را صریحاً «درخواست مستقیم کاربر نیست» اعلام کنید.
- **محدودیت نوشتن کامل:** در نوشتن کل فایل، جای‌نگهدار ممنوع است.

## چه چیزهایی را نباید عیناً کپی کرد

- **پروتکل ابزار XML:** فقط وقتی ارزش دارد که function calling بومی نباشد؛ پلتفرمی که ابزار بومی دارد باید از طرحوارهٔ بومی استفاده کند.
- **تأیید دستی اجباری هر قدم:** خط لولهٔ تمام‌خودکار را کند می‌کند و باید بسته به نوع محصول به بازگرداندن خودکار نتیجه تغییر کند.
- **مسیر Windows و `c:/Projects/JustGains-Admin`:** این‌ها مقدارهای محیط یک جلسهٔ واقعی‌اند و هنگام استفاده مجدد باید پارامتری شوند. نشانی `/test/path` هم در یک بند خراب آمده و باقی‌ماندهٔ قالب آزمایشی است.
- **ارزش «کم‌ترین تغییر»:** برای نگهداری کدبیس موجود است؛ در سناریوی تولیدی باید عکسش را تنظیم کنید.
- **بخش رابط کاربری ابتدای منبع:** تنظیمات افزونه است، نه پرامپت.

## موضوع‌هایی برای درس‌های بعدی

1. بدون function calling بومی، چطور پروتکل ابزار قابل‌تجزیه با XML یا Markdown طراحی کنیم.
2. توضیح ابزار را چطور بنویسیم که خطای فراخوانی کم شود (علامت پارامتر + نمونهٔ درست و نادرست).
3. چندعاملی سبک با «نقش + ماتریس دسترسی» (نمونه: حالت Boomerang).
4. طراحی امنیت Agent: اجرای تک‌قدمی، جعبه‌شنی پوشه، نوشتن کامل و خودبازبینی پیش از اتمام.
5. پیاده‌سازی بارگذاری لایه‌ای دستورها (قواعد سراسری، قواعد حالت، بازنویسی کامل).

> نکته: مسیرها و اطلاعات سیستم در این منبع عکس لحظه‌ای یک جلسه‌اند و فقط برای یادگیری ساختار به کار می‌آیند، نه به‌عنوان پیکربندی. برای مقایسه [Cline](../cline/lesson.md) و [Claude Code](../claude-code/lesson.md) را کنارش بخوانید.
