# درسنامهٔ پرامپت سیستمی VSCode Agent (GitHub Copilot)

## در یک جمله

این پرامپت سیستمی GitHub Copilot است وقتی در VS Code به‌عنوان «Agent کدنویسی خودکار» اجرا می‌شود. ارزش اصلی‌اش این است که نشان می‌دهد یک Agent کدنویسِ **عمیقاً گره‌خورده به مجموعه ابزار IDE** چطور با برچسب‌های ساختاریافته، هویت، انضباط ابزار، قواعد ویرایش و تزریق context را تمیز از هم جدا می‌کند.

## چرا ارزش یادگرفتن دارد

- **از کامل‌ترین نمونه‌های مجموعه ابزار بومی IDE است**: فقط «کد بلد است» کلی نیست؛ مجموعهٔ کاملی از توانایی‌های VS Code را، از جست‌وجوی معنایی، خواندن و تغییر فایل، اجرای ترمینال، گرفتن خطا، یافتن ارجاع تا ساختن فضای کاری، به شکل JSON Schema فهرست کرده است. برای بررسی «Agent چطور IDE را می‌راند» مرجع باکیفیتی است.
- **قیدهای سخت پرتراکم نوشته شده‌اند**: با انبوهی NEVER، MUST و DO NOT رفتارهای خطاخیز (مثل چاپ بلوک کد به جای فراخوانی ابزار، یا فراخوانی موازی semantic_search) یکی‌یکی میخ‌کوب شده‌اند؛ برای یادگرفتن «چطور با پرامپت رفتار مدل را محدود کنیم» مناسب است.
- **بخش‌بندی روشن**: با برچسب‌های XML مثل `<identity>`، `<instructions>`، `<toolUseInstructions>`، `<editFileInstructions>`، `<functions>` و `<context>` وظیفه‌ها را برش داده؛ اسکلت سازمان‌دهی پرامپتی که مستقیم قابل‌استفاده است.

## ساختار پرامپت، بخش به بخش

### ۱. تعریف هویت (`<identity>`)

- **مشکلی که حل می‌کند**: هویت برند را ثابت می‌کند (باید جواب بدهد «GitHub Copilot»)، به سیاست محتوایی Microsoft گره می‌زند و لحن را تعیین می‌کند (کوتاه و غیرشخصی).
- **چرا مؤثر است**: «قالب رد» را به یک جملهٔ ثابت تبدیل کرده، `"Sorry, I can't assist with that."`، تا مدل در موقعیت‌های مرزی آزادانه بداهه‌گویی نکند و خروجی پیش‌بینی‌پذیر باشد.
- **قابل‌استفادهٔ دوباره**: چهارگانهٔ «هویت + سیاست محتوا + جملهٔ ثابت رد + لحن» قالب استاندارد بخش هویت دستیارهای تجاری است.
- **کپی نکنید**: نام برند و سازندهٔ سیاست محتوا مخصوص Copilot‌اند و در محصول دیگر باید عوض شوند.

### ۲. دستورهای رفتار و مرز امنیتی (`<instructions>` + `<toolUseInstructions>`)

- **مشکلی که حل می‌کند**: مدل در حالت تردید **اول context جمع کند و بعد دست به کار شود**، و اقدام را اجباراً با ابزار انجام دهد، نه با توصیف زبانی.
- **قیدهای کلیدی**:
    - «مسئولیت توست (YOUR RESPONSIBILITY) که context جمع کنی»؛ پیش‌قدمی را به وظیفه تبدیل کرده.
    - «هرگز بلوک کدی با تغییر فایل یا دستور ترمینال چاپ نکن»؛ جلوی «وانمود به اجرا» را می‌گیرد.
    - «هرگز نام ابزار را به کاربر نگو»؛ پیاده‌سازی داخلی از کاربر پنهان می‌ماند و به جایش زبان طبیعی به کار می‌رود («دستور را در ترمینال اجرا می‌کنم»).
    - دو قاعدهٔ «semantic_search را موازی فراخوانی نکن» و «run_in_terminal را چند بار موازی نکن»؛ انضباط هم‌زمانی برای ابزارهای مشخص.
- **چرا مؤثر است**: هر قاعده به یک الگوی شکست واقعی و پرتکرار پاسخ می‌دهد؛ هدفمند و قابل‌اجراست.
- **قابل‌استفادهٔ دوباره**: «اول کاوش بعد اجرا + اولویت با ابزار + پنهان کردن نام ابزار» قالب انضباطی است که برای هر Agent داخل IDE یا CLI کاربرد دارد.

### ۳. فراخوانی ابزار (`<functions>`)

- **مشکلی که حل می‌کند**: با JSON Schema سخت‌گیرانه مجموعه‌ای از ابزارها را در اختیار می‌گذارد که کل زنجیره را پوشش می‌دهند: بازیابی (semantic_search، grep_search، file_search، list_code_usages)، خواندن و نوشتن (read_file، insert_edit_into_file)، اجرا (run_in_terminal، get_terminal_output)، تشخیص (get_errors)، اسکلت‌سازی پروژه (create_new_workspace، get_project_setup_info، install_extension) و شبکه (fetch_webpage).
- **چرا مؤثر است**: در description هر ابزار مستقیم نوشته «کی استفاده کن و کی نکن» (مثلاً grep برای رشتهٔ دقیق معلوم و semantic_search برای زبان طبیعی) و منطق انتخاب ابزار را به schema منتقل کرده تا استفادهٔ اشتباه کم شود.
- **قابل‌استفادهٔ دوباره**: «در توضیح ابزار موقعیت مناسب و نامناسب را روشن بنویس» ترفند کم‌هزینه و پربازدهی برای کم کردن فراخوانی اشتباه ابزار است.

### ۴. قواعد ویرایش فایل (`<editFileInstructions>`)

- **مشکلی که حل می‌کند**: «چطور کد را امن تغییر دهیم» را قاعده‌مند می‌کند: اول بخوان بعد تغییر بده، بر اساس فایل گروه‌بندی کن، بعد از تغییر حتماً خطا را بررسی کن (get_errors)، و با `// ...existing code...` ناحیهٔ تغییرنکرده را نشان بده تا کل فایل تکرار نشود.
- **چرا مؤثر است**: با نمونهٔ مشخص کلاس Person شیوهٔ حذف را نشان می‌دهد و قاعدهٔ انتزاعی را به الگوی قابل‌تقلید تبدیل می‌کند؛ و چرخهٔ «ویرایش ← راستی‌آزمایی ← رفع ← راستی‌آزمایی دوباره» را می‌سازد.
- **قابل‌استفادهٔ دوباره**: «کمترین diff + نشانهٔ حذف + بررسی اجباری بعد از ویرایش» الگوی طلایی مرحلهٔ ویرایش Agent کدنویس است.

### ۵. تزریق context (`<context>` + `<reminder>` + `<tool_format>`)

- **مشکلی که حل می‌کند**: محیط زمان اجرا (تاریخ، سیستم‌عامل، مسیر و ساختار فضای کاری) را پویا در پرامپت می‌گذارد تا مدل بر اساس محیط واقعی تصمیم بگیرد؛ `<reminder>` هم در انتهای پرامپت بلند، قاعدهٔ ویرایشی را که بیش از همه فراموش می‌شود دوباره تأکید می‌کند.
- **چرا مؤثر است**: تکرار در انتها از حساسیت بیشتر مدل به محتوای ابتدا و انتها استفاده می‌کند و قیدهای کلیدی را تقویت می‌کند.
- **قابل‌استفادهٔ دوباره**: «بخش context زمان اجرا + تکرار قاعدهٔ کلیدی در reminder پایانی» برای پرامپت‌های سیستمی بلند خیلی کاربردی است.

## الگوهای قابل‌استفادهٔ دوباره

- **اسکلت بخش‌بندی با برچسب XML**: `identity / instructions / toolUseInstructions / editFileInstructions / functions / context` با وظیفهٔ واحد برای هر بخش و اضافه و حذف آسان.
- **توضیح ابزار همراه با راهنمای انتخاب**: در description هر ابزار بنویس «کی استفاده کن و کی نکن».
- **سه‌بخشی قید رفتاری**: انگیزه (چرا) + واژهٔ وجهی قوی (MUST، NEVER) + مثال نقض (بلوک کد چاپ نکن).
- **چرخهٔ ویرایش**: بخوان ← تغییر بده (کمترین diff) ← get_errors ← رفع کن ← دوباره بررسی کن.
- **جملهٔ ثابت رد**: امنیت محتوا را به یک جملهٔ ثابت واحد محدود کن.

## چه چیزهایی را نباید عیناً کپی کرد

- **گره خوردن به برند و سیاست**: بخش هویت، سیاست محتوایی Microsoft و نام Copilot محتوای اختصاصی‌اند.
- **ابزارهای مخصوص VS Code**: get_vscode_api، install_extension، create_new_jupyter_notebook و مانند آن به‌شدت به میزبان VS Code وابسته‌اند و در محیط دیگر بی‌معنی‌اند.
- **مسیرهای واقعی در نمونه‌ها**: `c:\Users\Lucas\...` دادهٔ زمان اجرای لحظهٔ گردآوری است، نه محتوای قالب پرامپت؛ کپی کردنش گمراه‌کننده است.
- **مطلق کردن انضباط هم‌زمانی**: قاعده‌ای مثل «هرگز semantic_search را موازی نکن» در خدمت یک پیاده‌سازی مشخص است و با عوض شدن زیرساخت لزوماً کاربرد ندارد.

## موضوع‌هایی برای درس‌های بعدی

1. **طراحی مجموعه ابزار برای Agent داخل IDE**: با همین ابزارها به‌عنوان نمونه، لایه‌بندی بازیابی، خواندن و نوشتن، اجرا و تشخیص را توضیح دهید.
2. **توضیح ابزار همان مسیریاب است**: با مقایسهٔ توضیح grep_search و semantic_search نشان دهید «چطور با توضیح، مدل را به انتخاب ابزار درست هدایت کنیم».
3. **چرخهٔ امن ویرایش کد**: کالبدشکافی «اول بخوان بعد تغییر بده + نشانهٔ حذف + بررسی با get_errors».
4. **شیوهٔ نوشتن پرامپت با قید سخت**: جمع‌بندی زمان استفاده از NEVER و MUST و ترفند همراه کردنشان با مثال نقض.
5. **تزریق context زمان اجرا**: سرهم کردن پویای `<context>` و راهبرد تکرار در reminder پایانی.

> نکته: منبع این متن گردآوری جامعهٔ کاربران است و منبع رسمی‌اش مشخص نشده؛ آن را نسخهٔ رسمی و معتبر ندانید.
